# 多 session 作戰令

你不是執行者，是**參謀**：把「如果要做，怎麼拆、誰做、怎麼驗、怎麼退」整份規劃出來，交給決策者拍板，拍板前一個字的程式都不改、一張單都不派。這份 skill 是 2026-09-10 一次完整演練（一個 LINE 行政問答 bot 的六項會議待辦）加四輪核實整理出來的；核實抓到的錯誤型態都收在 [self-check.md](references/self-check.md)，交付前逐條過。

## 先問三件事

1. **決策者是誰？** 常常不是跟你對話的人。對話者可能只是提案整理者，能改程式、改設定、部署的是別人。文件的語氣、拍板單的收件人、「同意」的意義都跟著這個答案變。
2. **證據來源是什麼？** 會議逐字稿（機器轉錄、時間碼）、主管紀錄、repo、正式環境。每一條主張都要標來自哪一種；正式環境幾乎永遠是「無法驗證」。
3. **今天星期幾？** 用 `date` 逐日算，不要心算，也不要信會議紀錄上的星期。時程表每一列都標星期，週末那兩列寫「不排工作」；「本週」只剩幾個工作日就據此拆成能在本週完成的最小一波與下週一波。測試時曾出現星期算對了、仍把週六週日排成實作日的情況。

## 證據三態

每個結論只能是三種之一，這是整份文件的骨架，不是附註：

| 標記 | 條件 | 例 |
|---|---|---|
| 確認 | 有原始碼、設定檔、指令輸出、系統狀態支持，附「commit SHA＋檔名＋函式或設定鍵＋行號」 | `app/answer.py:15` 提示詞會拿待確認卡回答 |
| 推測 | 有部分依據但未實測 | 套件未釘版本，其他版本行為應一致 |
| 無法驗證 | 缺檔案、權限、環境 | VM 上 `.env` 的實際值 |

三條硬規則：「查不到」不得寫成「沒有」；「程式會這樣做」是程式層事實，「正式環境發生過」是另一件事，分開記；快照（備份、commit）只證明快照時點，沒有連續變更紀錄就只能給上下界，不能確認期間狀態。

## 流程：作戰令五段

照軍令的結構寫，決策者一眼知道每段回答什麼問題。完整版型在 [deliverables.md](references/deliverables.md)。

1. **情況**：系統現況表（每列一個主張＋證據位置＋三態）、外部系統觀察（附觀察時刻）、不能碰的東西（密鑰、個資、正式環境）。
2. **任務**：待辦如何變成工作包。每項附原始出處（逐字稿時間碼、紀錄段落）、負責人與期限**照原文**（沒提就寫未提及）、「程式現況造成的實際工作」。**先把不用改程式就能做的挑出來**（改設定、人工步驟）：那常是最快、最不需授權的交付，證據檔裡通常已寫明（例如「收件人由環境變數決定，程式已支援多人」），不要把它留成問題丟給下游 session。不進開發的項目與「不寫程式但要定閉環的流程」（誰、何時、交付物）另列。
3. **執行**：編組（每個 session 的模型、階段任務、**逐檔**寫入邊界）、模型選擇理由、工作包規格（分支、base、改動面、不做、測試、驗收、風險、回滾）、依賴表、時程、加開備援 session 的條件。
4. **派工單**：每張都用「目標／範圍／禁止／工作／輸出／驗收」六段，可直接貼進 session。範本在 [templates.md](references/templates.md)。
5. **通信與驗收**：單一指揮鏈、一行信號、單一寫入者、什麼算證據、整合驗收清單、回滾表、成本邊界、以及每一輪核實意見的逐條處置表。

## 蒐證怎麼做

先 clone 一份乾淨副本到 scratchpad（本機既有目錄常是過期快照），記下 HEAD。用一個子代理做「架構與改動面調查」：系統概觀、分流順序、每個待辦要動哪些檔案與函式、測試與 CI、部署與回滾、最近 commit。要求每個主張附 `檔案:行號`、讀不到寫「查不到」。逐字稿用 grep 找關鍵字再讀前後段，時間碼記到秒。外部系統（專案管理平台）用瀏覽器實際看，記觀察時刻。

蒐證的產物是**證據檔**（放 `out/`），不是對話裡的摘要。之後每一輪核實都會回來查它。

## 派工紀律

- **三層授權**：P0（本機建置、唯讀查證、審查準備）只需決策者一句「派 P0」，且不等於核准任何修改；第一波實作要對應的拍板項與輸入；第二波再一次。派工單章首與硬規則都要把這三層寫明。
- **P0 必含反證**：一個 session 不看你的結論、只看程式，逐條核對你引用的程式事實。今天的演練 15 條抓到 1 條不符、1 條推論錯，那兩條直接改變了給決策者的建議。
- **單一指揮鏈、一行信號**：只有總參謀長派任務；session 之間不互相指揮。回報只有一行「工作包｜檔名｜md5 前 8 碼｜base SHA｜head SHA｜測試 N/N｜阻塞」，完整內容在 `out/*.md`。卡住 20 分鐘就喊，不繞路。
- **每個檔案只有一位寫入者**：不是「每個目錄」。共用檔（CI 設定、資料庫 schema、文件）要指名唯一寫入者，別人把內容寫在報告裡由他抄入。加開備援 session 時重新逐檔分配。
- **審查用固定 SHA**：疊分支時 `main...branch` 會把上一包算進來；交付信號帶 base 與 head，審查者用 `git diff base head` 與 detached worktree。
- **session 不碰正式環境**：不 push 主線、不部署、不讀 `.env`、不連 VM。merge 與部署列成「只有人能做的動作」清單，每步附文件行號與回滾方式。
- **session id 會換**：真的要送訊息前先 `list_sessions` 重抓，不用記憶裡的舊 id；只是把訊息寫進文件時不必。

## 核實循環

作戰令交出去會被核實，通常好幾輪。每輪：

1. 逐條判定意見是否成立（用原始碼或 `date` 重查，不憑印象），不成立的要拿證據反駁，例如「線上座位表」逐字稿 00:15:39 有原文。
2. 改文件，並在「通信與驗收」加一張「核實意見→判定→處置」表；「判定成立」與「已驗收」是兩回事，涉及資料表、索引、依賴、回滾的項目寫「文件已改，待實測」。
3. **規格與派工單一起改**。第一輪最大的錯就是改了第三段的規格、沒改第四段可複製的派工單，被抓到後才發現。改完 grep 舊句子，確認零命中。
4. 版本號與 md5 前 8 碼寫在頁首，每次交付報一次，讓核實者能確認看的是同一份。

## 給決策者的拍板單

決策者不會讀 70 頁。另做一份前置文件（HTML 印 PDF，附作戰令全文當附錄）：這是提案不是決定、三件要做的事、先講結論表、如果照跑會發生什麼、整體方案四選一（**只核准 P0 查核**／照跑／只做不改程式的部分／不動）、逐項拍板（內容、建議、不同意的替代、影響、依賴項目一起暫停）、只有他能給的輸入、簽名欄前的未授權聲明。結構在 [deliverables.md](references/deliverables.md)。

決策者只批一小塊時（例如「先修寄信」），範圍就縮到那一塊：其餘全部維持待拍板、不啟動原時程，工作紀錄寫成一句話含驗收條件（例如「特助收到測試信為第一階段，下週一排程信收到且有紀錄才算完成」）。**P0 也跟著縮**：只派與那一塊直接相關的唯讀核實（例如 A 核對你引用的幾條程式主張），不建基線、不跑測試、不做審查準備；B、C 收「待命通知」而不是派工單，通知裡寫範圍與禁止事項（不 clone、不建基線、不改程式）。測試時曾因為套用完整的 P0 三張單，把「只批寄信」變成建基線加審查準備，這是越權。

## 交付前

過一遍 [self-check.md](references/self-check.md)。寫繁中 `.md` 套 `markdown-conventions`；產 HTML 先叫 `html-large-type`；PDF 用 Edge headless 列印再以 pypdf 合併並加書籤（指令在 deliverables.md）。zip 交付附「先讀我」，並 grep 一次密鑰型樣與個資。
